Office Power 설치 및 장애 대응 안내서
사무실·현장 Windows PC 전원 관리
작성 기준: 2026-10-20 / WinForms / Windows 10·11 x64

============================================================
1. 설치 전에 알아둘 사항
============================================================
사용법: PowerShell 명령은 [복사 시작]과 [복사 끝] 사이 전체를 한 번에 복사한다.
표시 줄 자체는 복사하지 않는다. 명령은 한 줄씩 따로 실행할 필요가 없다.
IP·폴더·랜카드 번호는 실행 중 질문이 나오면 입력한다.
진단은 조회만 한다. 설정 변경은 별도 '해결용' 블록에서만 실행한다.

관리 PC: Controller를 실행해서 다른 PC를 켜고 끄는 컴퓨터.
대상 PC: Agent를 설치해서 제어받는 컴퓨터.

현재 프로그램은 관리 PC와 대상 PC가 같은 LAN에 있는 구성을 기본으로 한다.
사무실과 떨어진 현장에는 현장 LAN 안의 관리 PC에서 Controller를 사용한다.
사무실에서 다른 현장까지 직접 제어하는 기능은 별도 네트워크 구성이 필요하다.
VPN이 있어도 WOL 브로드캐스트가 자동 전달되는 것은 아니다.
다른 VLAN·서브넷이면 네트워크 담당자와 VPN·현장 내 WOL 중계 등을 검토한다.
인터넷 공유기에 Agent 포트를 직접 개방하지 않는다.

필수 조건:
- 대상 PC는 유선 LAN 사용 권장. 일반 Wi-Fi로 종료 상태 WOL이 된다고 가정하지 않는다.
- 전원 케이블·멀티탭 전원을 유지한다. 전원이 완전히 끊기면 WOL은 불가능하다.
- BIOS와 유선 랜카드가 종료 상태 Wake-on-LAN을 지원해야 한다.
- 설치·제거·방화벽·네트워크 설정 변경은 대상 PC의 관리자 권한이 필요하다.
- 현장 장비나 제어 설비가 연결된 PC는 현장 담당자와 종료 가능 시간을 확인한다.

2. 배포본 만들기: 개발 PC에서 한 번
============================================================
Git Pull 후 실행 중인 Controller·AgentSetup과 VS 디버깅을 종료한다.
개발 PC의 PowerShell에 아래 전체를 한 번에 붙여넣는다.
기본 위치가 맞으면 Enter, 다르면 실제 office-power 폴더를 입력한다.

[복사 시작: 개발 PC 배포본 만들기]
& {
    $projectFolder = Read-Host 'office-power 폴더 (기본 E:\kohya_ss\office-power / Enter 사용)'
    if ([string]::IsNullOrWhiteSpace($projectFolder)) { $projectFolder = 'E:\kohya_ss\office-power' }
    $publisher = Join-Path $projectFolder 'scripts\Publish-Windows.ps1'
    if (-not (Test-Path -LiteralPath $publisher)) { Write-Host '폴더가 올바르지 않습니다.'; return }
    Push-Location -LiteralPath $projectFolder
    try {
        powershell.exe -NoProfile -ExecutionPolicy Bypass -File $publisher
        if ($LASTEXITCODE -ne 0) { Write-Host '배포 실패. 위 오류를 확인하세요.'; return }
        Write-Host ('완료: ' + (Join-Path $projectFolder 'artifacts\OfficePower-win-x64'))
    } finally { Pop-Location }
}
[복사 끝]

생성 위치:
E:\kohya_ss\office-power\artifacts\OfficePower-win-x64

대상 PC에 복사할 것: AgentSetup.exe 파일 하나.
관리 PC에 복사할 것: Controller 폴더 전체.
ZIP 생성·압축 해제는 필요 없다.
배포본에 런타임이 포함되므로 실행 PC에는 별도 .NET SDK 설치가 필요 없다.
VS2022 일반 빌드 출력과 위 스크립트로 만든 배포본은 다르다.

개발 PC 빌드 조건:
- VS2022 17.11 이상 및 .NET 데스크톱 개발·ASP.NET 및 웹 개발 워크로드.
- global.json에 맞는 .NET 8 SDK. 현재 기준 8.0.426.
- .NET 9 SDK만 설치되어 있으면 NETSDK1141이 발생할 수 있다.
  해결: .NET 8 SDK를 추가 설치한다. 런타임 설치만으로는 빌드할 수 없다.
  설치한 SDK 확인이 필요하면 아래를 한 번 복사한다.

[복사 시작: 개발 PC SDK 확인]
& { dotnet --list-sdks }
[복사 끝]

3. 대상 PC 설치·업데이트·제거
============================================================
1) 대상 PC에서 AgentSetup.exe를 더블클릭한다.
2) 관리자 권한 요청을 승인한다.
3) [설치 / 업데이트]를 누르고 완료를 기다린다.
4) 화면의 PC 이름·IP를 확인한다.
5) [등록 파일 저장]으로 USB 등 원하는 위치에 JSON을 저장한다.
6) 이 JSON을 관리 PC로 안전하게 전달한다.

기존 Agent를 먼저 삭제할 필요는 없다.
새 설치 프로그램이 기존 서비스를 중지하고 업데이트 후 다시 시작한다.
기존 인증키·인증서를 유지하므로 등록된 Controller에서 보통 재등록할 필요가 없다.
업데이트 실패 시 설치 창의 오류를 기록하고 다시 실행한다.
성공 안내가 나오기 전에 창을 강제 종료하지 않는다.
Agent EXE를 직접 더블클릭하는 것은 서비스 설치 방법이 아니다.

서비스 이름: OfficePowerAgent
설치 위치: C:\Program Files\OfficePowerAgent
서비스는 PC 시작 시 자동 실행된다. 설치 프로그램을 매번 실행할 필요는 없다.

제거: 대상 PC에서 AgentSetup.exe 실행 → [서비스 제거].
서비스와 방화벽 규칙만 제거하고 프로그램 파일·인증 정보는 보존한다.
Controller의 목록 삭제는 대상 PC의 Agent 제거와 별개다.
이 설치 프로그램은 다른 PC에 원격 접속해서 제거하지 않는다.

4. Controller 등록·데이터 보관
============================================================
1) 관리 PC에서 Controller 폴더의 OfficePower.Controller.exe를 실행한다.
2) [PC 등록] → [인증 파일 가져오기]에서 대상 PC의 JSON을 선택한다.
3) 이름·현재 IP·유선 랜카드 MAC·브로드캐스트 주소를 확인하고 저장한다.
4) Controller는 시작할 때 등록된 PC 전체의 연결을 자동 확인한다.
5) 이후 PC를 체크하고 [연결 확인]으로 상태를 다시 확인할 수 있다.

인증 파일 이름 예:
SITE-A-PC01-pairing.json
SITE-A-PC02-pairing.json
파일명 앞부분은 생성한 컴퓨터의 이름이다.
현장별로 컴퓨터 이름을 구분하거나 전달용 폴더를 나누면 혼동을 줄일 수 있다.

대상 PC의 원본 인증 파일:
C:\Program Files\OfficePowerAgent\컴퓨터이름-pairing.json
보호된 폴더이므로 직접 찾기보다 설치 화면의 [등록 파일 저장]을 사용한다.
이전 버전은 C:\ProgramData\OfficePowerAgent\pairing.json을 사용했다.
최신 Agent는 이전 인증 자료를 유지하며 새 설치 폴더로 옮긴다.

관리 PC의 등록 데이터:
Controller 실행 파일 옆의 RemoteData\computers.json
폴더는 처음 저장할 때 생성된다.

예:
D:\OfficePower\Controller\OfficePower.Controller.exe
D:\OfficePower\Controller\RemoteData\computers.json

이전 AppData 자료를 옮길 경우:
- Controller를 종료한다.
- Win+R → %LOCALAPPDATA%\OfficePower 를 연다.
- computers.json을 실행 파일 옆 RemoteData 폴더에 직접 복사한다.
- 자동 이전 기능은 없다. 기존 파일이 있으면 덮어쓰기 전에 백업한다.

중요: 인증키는 Windows DPAPI로 암호화된다.
RemoteData를 옮겨도 같은 PC·같은 Windows 계정에서만 복호화할 수 있다.
다른 현장 관리 PC나 다른 계정에서는 PC별 인증 JSON을 다시 가져와 등록한다.
인증 JSON은 전원 제어 권한이므로 공개 저장소·단체 채팅에 올리지 않는다.
Controller를 업데이트할 때 RemoteData 폴더를 삭제하지 않는다.
쓰기 권한이 없는 폴더에서 Controller를 실행하면 저장이 실패할 수 있다.
관리 계정이 쓸 수 있는 전용 폴더에 두고 사용한다.

5. 응답 시간 초과·연결 실패: 가장 먼저 할 점검
============================================================
먼저 관리 PC에서 아래 전체를 한 번 복사한다.
실행 후 문제가 있는 대상 PC의 IP를 입력한다. 포트는 자동으로 18765를 사용한다.

[복사 시작: 관리 PC 연결 진단]
& {
    $remoteIp = Read-Host '연결할 대상 PC의 IP를 입력하세요'
    $parsedAddress = $null
    if (-not [Net.IPAddress]::TryParse($remoteIp, [ref]$parsedAddress) -or $parsedAddress.AddressFamily -ne [Net.Sockets.AddressFamily]::InterNetwork) {
        Write-Host '올바른 IPv4 주소를 입력해야 합니다.'; return
    }
    Test-NetConnection -ComputerName $remoteIp -Port 18765
}
[복사 끝]

확인 항목:
- TcpTestSucceeded : True → TCP 접속 성공. 인증·인증서·서비스 응답을 추가 확인한다.
- PingSucceeded : True, TcpTestSucceeded : False
  → PC는 응답하지만 포트 접속은 실패. 서비스·리스닝·방화벽을 확인한다.
- Ping 실패만으로 전원이 꺼졌다고 판단하지 않는다. ICMP 차단일 수도 있다.

다음은 문제가 있는 대상 PC의 '관리자 PowerShell'에서 한 번 복사한다.
서비스·네트워크 종류·IP·MAC·대기 포트·방화벽·인증 파일 위치를 한꺼번에 출력한다.
설정을 바꾸거나 인증키 내용을 출력하지 않는다.

[복사 시작: 대상 PC 전체 진단]
& {
    Write-Host "`n===== Agent 서비스 ====="
    $service = Get-Service -Name OfficePowerAgent -ErrorAction SilentlyContinue
    if ($service) { $service | Format-Table Status, Name, DisplayName -AutoSize } else { Write-Host 'Agent 서비스 없음' }
    Write-Host "`n===== 네트워크 프로필 ====="
    Get-NetConnectionProfile | Format-Table InterfaceIndex, InterfaceAlias, Name, NetworkCategory -AutoSize
    Write-Host "`n===== 랜카드 IP ====="
    Get-NetIPAddress -AddressFamily IPv4 | Format-Table InterfaceIndex, InterfaceAlias, IPAddress, PrefixLength -AutoSize
    Write-Host "`n===== 랜카드 MAC ====="
    Get-NetAdapter | Format-Table ifIndex, Name, Status, MacAddress -AutoSize
    Write-Host "`n===== TCP 18765 대기 상태 ====="
    $listeners = Get-NetTCPConnection -LocalPort 18765 -State Listen -ErrorAction SilentlyContinue
    if ($listeners) { $listeners | Format-Table LocalAddress, LocalPort, OwningProcess -AutoSize } else { Write-Host '대기 중인 포트 없음' }
    Write-Host "`n===== Agent 방화벽 ====="
    $rule = Get-NetFirewallRule -Name OfficePowerAgent-LAN -ErrorAction SilentlyContinue
    if ($rule) { $rule | Format-Table Enabled, Profile, Direction, Action -AutoSize } else { Write-Host 'Agent 방화벽 규칙 없음' }
    Write-Host "`n===== 등록 파일 위치 ====="
    $agentFolder = Join-Path $env:ProgramFiles 'OfficePowerAgent'
    $pairingFiles = Get-ChildItem -LiteralPath $agentFolder -Filter '*pairing.json' -ErrorAction SilentlyContinue
    if ($pairingFiles) { $pairingFiles | Select-Object FullName | Format-List } else { Write-Host '등록 파일 없음' }
}
[복사 끝]

판단:
- 서비스가 없음: AgentSetup.exe에서 설치한다.
- Stopped: AgentSetup.exe에서 [설치 / 업데이트]를 다시 실행한다.
- Running인데 Listen 결과가 없음: 잠시 기다렸다 다시 진단한다.
  계속 없으면 설치 오류·이벤트 뷰어와 포트 충돌 등을 점검한다.
- IP가 바뀜: Controller의 등록 IP를 현재 IP로 수정한다.
- 랜카드가 여러 개: 실제 현장 유선 LAN의 IP·MAC 조합인지 확인한다.

실제 발생했던 사례:
서비스는 Running, Ping은 성공했지만 대상 PC의 네트워크가 Public이었다.
현재 Agent 방화벽 규칙은 Private·Domain + LocalSubnet만 허용한다.
따라서 Public 상태에서는 접속이 차단될 수 있다.

해결: 신뢰하는 사무실·현장 LAN인 경우에만 해당 연결을 Private로 바꾼다.
아래 전체를 대상 PC의 관리자 PowerShell에 한 번 복사한다.
표에서 실제 유선 연결의 InterfaceIndex를 골라 입력하고 YES로 변경을 확인한다.
공용 Wi-Fi·외부망까지 일괄 변경하지 않는다.
도메인 정책이 적용된 PC는 현장 네트워크 관리자에게 확인한다.

[복사 시작: 대상 PC 해결용 / 선택한 Public 연결만 Private로 변경]
& {
    Get-NetConnectionProfile | Format-Table InterfaceIndex, InterfaceAlias, Name, NetworkCategory -AutoSize
    $indexText = Read-Host '신뢰하는 현장 유선 LAN의 InterfaceIndex를 입력하세요'
    $networkIndex = 0
    if (-not [int]::TryParse($indexText, [ref]$networkIndex)) { Write-Host '정수 번호를 입력해야 합니다.'; return }
    $profile = @(Get-NetConnectionProfile -InterfaceIndex $networkIndex -ErrorAction SilentlyContinue)
    if ($profile.Count -ne 1) { Write-Host '연결을 하나로 확인할 수 없습니다. 대상 번호를 다시 확인하세요.'; return }
    if ($profile[0].NetworkCategory -ne 'Public') { Write-Host 'Public 연결이 아니므로 변경하지 않았습니다.'; return }
    $profile | Format-Table InterfaceIndex, InterfaceAlias, Name, NetworkCategory -AutoSize
    $answer = Read-Host '위 연결이 신뢰하는 현장 LAN이면 YES 입력 (그 외 취소)'
    if ($answer -cne 'YES') { Write-Host '취소했습니다.'; return }
    try {
        Set-NetConnectionProfile -InterfaceIndex $networkIndex -NetworkCategory Private -ErrorAction Stop
        Get-NetConnectionProfile -InterfaceIndex $networkIndex | Format-Table InterfaceIndex, InterfaceAlias, NetworkCategory -AutoSize
        Write-Host '변경 완료. 관리 PC에서 연결 진단 또는 Controller 연결 확인을 다시 실행하세요.'
    } catch { Write-Host ('변경 실패: ' + $_.Exception.Message) }
}
[복사 끝]

변경 후 관리 PC에서 연결 진단 블록을 다시 실행하고 Controller [연결 확인].
이 프로필 변경만을 위해 Agent를 재설치할 필요는 없다.

기본 통신: HTTPS TCP 18765. WOL 패킷은 UDP 9.
방화벽 전체를 끄지 말고 해당 규칙과 네트워크 구간을 확인한다.
여전히 실패하면 VLAN·망 분리·보안 프로그램·무선 클라이언트 격리를 점검한다.

6. 인증 실패·등록 파일 없음·데이터 읽기 실패
============================================================
[인증 실패 또는 인증서 오류]
- 대상 PC의 최신 인증 JSON을 [등록 파일 저장]으로 다시 저장한다.
- Controller에서 해당 PC 등록을 수정해 JSON을 다시 가져온다.
- 다른 PC의 IP에 연결하고 있지 않은지 확인한다.
- PC 날짜·시간과 인증서 만료를 확인한다. 인증서는 생성 시 5년 유효하다.
- 인증 검증을 끄거나 알 수 없는 인증서를 무조건 신뢰하도록 변경하지 않는다.

[JSON이 안 보임]
- AgentSetup.exe에서 설치가 완료됐는지 확인한다.
- 복사한 EXE 폴더와 실제 설치 폴더는 다르다.
- [등록 파일 저장] 버튼을 먼저 사용한다.
- 대상 PC 전체 진단 블록의 마지막 '등록 파일 위치'에서 경로를 확인한다.
- 없다면 설치 화면 오류를 확인한다. 오래된 EXE를 복사했다면 배포본을 다시 만든다.

[Controller 등록 파일 읽기·복호화 실패]
- RemoteData\computers.json 원본을 백업하고 임의로 내용을 편집하지 않는다.
- 다른 PC·다른 계정에서 복사한 파일인지 확인한다.
- 다른 PC이면 원래 인증 JSON을 가져와 다시 등록한다.
- 읽기 실패 시 기존 자료 보호를 위해 편집이 막히는 것이 정상이다.

7. 끄기는 되는데 켜기가 안 됨: WOL 점검
============================================================
끄기는 Agent HTTPS 통신이고, 켜기는 랜카드·BIOS의 Wake-on-LAN이다.
Agent 설치만으로 BIOS와 랜카드 설정이 자동 변경되지는 않는다.

확인 순서:
1) 대상 PC의 AC 전원과 유선 랜선을 유지한다.
2) Controller의 MAC이 유선 랜카드의 MAC인지 확인한다.
   위 대상 PC 전체 진단 블록의 랜카드 IP·MAC 출력으로 확인한다.
3) Controller의 브로드캐스트 주소를 실제 서브넷에 맞춘다.
   예: IP 192.168.0.21, 마스크 255.255.255.0 → 192.168.0.255
   마스크가 다르면 주소도 달라진다. 모든 현장에 위 주소를 그대로 쓰지 않는다.
4) BIOS의 WOL·PCI-E/Network Wake 설정을 켠다.
5) Windows 유선 랜카드의 Magic Packet 설정과 빠른 시작을 확인한다.
6) 절전 상태에서 먼저 켜 보고, 종료 상태에서도 시험한다.
   절전에서는 되지만 종료 후 안 되면 S4/S5 설정·빠른 시작·하드웨어 지원을 확인한다.

Controller의 '켜기 요청 전송'은 패킷을 보냈다는 뜻이다.
실제 전원 투입·Windows 부팅 성공을 보장하는 응답은 아니다.
WOL에 응답 확인 프로토콜은 없으므로 본체 상태와 이후 [연결 확인]으로 판단한다.

[Windows 설정]
장치 관리자 → 네트워크 어댑터 → 실제 유선 랜카드 → 속성:
- 고급: Wake on Magic Packet → 사용.
- Shutdown Wake-On-Lan 같은 항목이 있으면 사용.
- 전원 관리: 장치로 컴퓨터를 깨우는 옵션과 Magic Packet만 허용 옵션 확인.
드라이버에 따라 항목 이름이 다르거나 전원 관리 탭이 없을 수 있다.
필요하면 PC 제조사의 유선 랜카드 드라이버를 확인한다.

제어판 → 전원 옵션 → 전원 단추 작동 설정
→ 현재 사용할 수 없는 설정 변경 → 빠른 시작 켜기 해제 → 저장.

[HP BIOS: 실제 확인한 화면 기준]
Power → Hardware Power Management:
- S4/S5 Wake on LAN → Enable. 실제 장애 PC에서는 Disable이라 켜지지 않았다.
Advanced → Power-On Options:
- Remote Wakeup Boot Source → Local Hard Drive.
- Wake on LAN Power-On Password Policy는 현장 암호 정책에 맞게 유지한다.
Network Boot는 PXE 네트워크 부팅 설정이다. WOL 전원 켜기와 별개다.
BIOS Power-On의 요일·시간은 예약 켜기이므로 WOL 용도로 켤 필요 없다.

[MSI Click BIOS 5: 실제 확인한 화면 기준]
Settings → Advanced → Wake Up Event Setup:
- Wake Up Event By → BIOS.
- Resume By PCI-E/Networking Device → Enabled.
Settings → Advanced → Power Management Setup:
- ErP Ready → Disabled (항목이 있는 모델).
Settings → Boot:
- 부팅 디스크가 우선인지 확인한다.
- MSI Fast Boot는 문제가 있을 때 Disabled로 바꿔 비교 시험한다.
  이 옵션이 모든 기종에서 원인인 것은 아니다.
변경 후 F10 → 저장 후 종료. 제조사·모델마다 메뉴 이름이 다를 수 있다.

============================================================
8. 본체 버튼보다 원격 켜기가 느릴 때
============================================================
원격 켜기와 본체 버튼을 같은 종료 상태에서 비교한다.
단순히 '원격은 느림'만으로 네트워크 부팅이 원인이라고 단정하지 않는다.

- 클릭 후 전원 LED·팬이 켜지기까지 오래 걸림:
  패킷 전달·브로드캐스트·랜카드 WOL 반응·스위치 구간 확인.
- 전원은 바로 켜지지만 BIOS 로고에서 지연:
  PXE 시도 메시지·장치 검사·부팅 우선순위·원격 부팅 소스 확인.
- Windows 화면까지는 빠르지만 Controller 연결이 늦음:
  네트워크 준비·Agent 서비스 시작과 방화벽 상태 확인.

네트워크 부팅을 사용하지 않는 PC에서 PXE 대기가 실제 보이면
Network Boot/PXE를 끄고 로컬 디스크 부팅을 우선하도록 시험할 수 있다.
현장에서 PXE로 OS 설치·복구하는 PC라면 담당자와 확인 후 변경한다.
네트워크 부팅 순서가 뒤라는 이유만으로 지연 원인을 확정하지 않는다.

============================================================
9. 종료가 늦음·종료가 안 됨·이미 예약됨
============================================================
최신 Agent는 요청을 받은 뒤 10초 후 종료를 예약한다.
10초가 지났다고 전원이 반드시 즉시 꺼지는 것은 아니다.
앱 종료·저장 확인·Windows 업데이트 등으로 실제 전원 차단까지 더 걸릴 수 있다.
사용 중인 앱을 강제 종료하도록 설정하지 않았다.

계속 30초로 표시되면 구버전 Agent일 수 있다.
Git Pull → 배포본 재생성 → 대상 PC에서 새 AgentSetup.exe로 업데이트한다.
Controller만 바꿔서는 대상 PC의 대기 시간이 변경되지 않는다.
Controller는 종료 응답의 실제 예약 초를 표시한다.

이미 종료가 예약됐다는 메시지:
중복 종료 요청은 2분 동안 거부된다.
종료가 취소·중단됐다면 작업 상태를 확인하고 2분 후 다시 요청한다.
OS 종료가 여전히 진행 중이면 새 요청이 실패할 수 있다.

============================================================
10. 설치·빌드 중 이미 겪었던 오류
============================================================
[Join-Path: Path가 빈 문자열]
오류 줄이 다음 코드이면 예전 설치 스크립트다.
param([string]$AgentSource = (Join-Path $PSScriptRoot 'Agent'))

해결: 최신 소스로 배포본을 다시 만들고 새 AgentSetup.exe를 사용한다.
Git Pull은 저장소 파일만 갱신한다. 다른 PC로 복사한 EXE·CMD·PS1은 갱신하지 않는다.
VS 일반 빌드도 예전에 복사해 둔 설치 스크립트를 자동 교체하지 않는다.
예전 CMD 설치를 계속 쓸 때는 최신 CMD·PS1을 함께 교체해야 한다.

[MSB4018 / GenerateBundle / 다른 프로세스에서 파일 사용 중]
출력 폴더의 Controller 등이 실행 중이라 EXE를 덮어쓸 수 없는 경우다.
Controller·설치 프로그램을 닫고 VS 디버깅도 중지한 뒤 다시 게시한다.
계속 사용해야 하면 새 출력 폴더로 게시한다.

[복사 시작: 개발 PC에서 다른 출력 폴더로 배포]
& {
    $projectFolder = Read-Host 'office-power 폴더 (기본 E:\kohya_ss\office-power / Enter 사용)'
    if ([string]::IsNullOrWhiteSpace($projectFolder)) { $projectFolder = 'E:\kohya_ss\office-power' }
    $outputFolder = Read-Host '새 배포 출력 폴더의 전체 경로를 입력하세요'
    if ([string]::IsNullOrWhiteSpace($outputFolder) -or -not [IO.Path]::IsPathRooted($outputFolder)) { Write-Host '전체 경로를 입력해야 합니다.'; return }
    $publisher = Join-Path $projectFolder 'scripts\Publish-Windows.ps1'
    if (-not (Test-Path -LiteralPath $publisher)) { Write-Host '저장소 폴더가 올바르지 않습니다.'; return }
    Push-Location -LiteralPath $projectFolder
    try {
        powershell.exe -NoProfile -ExecutionPolicy Bypass -File $publisher -OutputRoot $outputFolder
        if ($LASTEXITCODE -ne 0) { Write-Host '배포 실패. 위 오류를 확인하세요.'; return }
        Write-Host ('완료: ' + (Join-Path $outputFolder 'OfficePower-win-x64'))
    } finally { Pop-Location }
}
[복사 끝]

스크립트가 실패한 경우 남아 있는 출력 폴더에 구·신버전이 섞일 수 있다.
성공 메시지를 확인한 배포본만 전달한다.

[cdd를 찾을 수 없음]
폴더 이동 명령은 cdd가 아니라 cd이다.

[설치·파일 저장 권한 오류]
AgentSetup.exe의 관리자 권한 승인을 확인한다.
관리되는 PC의 보안 정책이 차단하면 해당 정책 담당자에게 오류를 전달한다.
Controller의 RemoteData는 현재 사용자가 쓰기 가능한 경로에 둔다.

[아이콘이 예전 것으로 보임]
최신 배포본으로 EXE를 교체하고 기존 바로가기도 대상 경로를 확인한다.
Windows 탐색기 아이콘 캐시 때문에 즉시 갱신되지 않을 수 있다.
프로그램 재실행·탐색기 새로 고침 후 확인한다.

11. 현장 설치 완료 점검표
============================================================
[ ] 현장명 / PC 이름 / 담당자 기록.
[ ] 유선 랜카드 IP·서브넷 마스크·MAC 기록 (비밀 인증키는 기록하지 않음).
[ ] IP 변경 방지를 위한 DHCP 예약 또는 관리된 고정 IP 적용.
[ ] AgentSetup 설치 완료 / OfficePowerAgent Running.
[ ] 관리 PC에서 TCP 18765 연결 성공.
[ ] Controller 등록 후 연결 정상.
[ ] 승인된 시간에 종료 요청·실제 종료 확인.
[ ] 완전 종료 상태에서 WOL 켜기 확인.
[ ] 부팅 후 Controller 연결 재확인.
[ ] 멀티탭·랜선 유지 조건을 현장 담당자에게 안내.
[ ] RemoteData 백업과 현장별 등록 JSON의 안전한 보관 위치 확인.
[ ] 문제가 발생하면 PC 기종·오류 문구·서비스·네트워크 프로필·포트 결과 기록.

담당자에게 전달할 진단 정보:
- 관리 PC / 대상 PC의 IP와 서브넷, 실제 유선 인터페이스.
- 대상 PC 제조사·모델·BIOS 설정 사진.
- Test-NetConnection의 PingSucceeded / TcpTestSucceeded.
- Get-Service OfficePowerAgent 결과.
- 해당 연결의 NetworkCategory와 설치 화면 오류.
인증 JSON 본문·Token·인증서 개인키·agent-settings.json 내용은 보내지 않는다.
